## Workflow 1: تسجيل مدرس جديد

**المصدر:** `teacher_features.md` (Section 2.1) + `admin_features.md` (Section 7)

### السيناريو الكامل

1. المدرس يزور صفحة التسجيل (`TeacherRegistrationController::store`).
2. يملأ البيانات المطلوبة (الاسم، الموبايل، كلمة المرور).
3. يتم إنشاء حساب جديد بخصائص:
   - `role = 'teacher'`
   - `status = 'pending'` (في انتظار موافقة الأدمن)
   - `teacher_code` يُولّد تلقائياً بشكل فريد (TC-XXXXXX)
   - `email` يُنشأ placeholder بناءً على الموبايل
4. عند التسجيل يُنشأ الترم الأكاديمي الأول تلقائياً (`AcademicTerm::createDefaultFor`).
5. لا يمكن للمدرس تسجيل الدخول حتى يتم تفعيل حسابه.
6. الحساب يظهر في صفحة طلبات المدرسين عند الأدمن (`GET /admin/teacher-requests`).
7. الأدمن يرى جميع المدرسين ذوي الحالة `pending`.
8. الأدمن يضغط على زر "موافقة" (`POST /admin/teachers/{user}/approve`).
9. النظام يتحقق: `$user->role === 'teacher'` و `$user->status === 'pending'`.
10. يتم تغيير الحالة إلى `active`.
11. يتم تسجيل العملية في Activity Log (`teacher_approved`).
12. المدرس يستطيع الآن تسجيل الدخول (`POST /login`).
13. بعد تسجيل الدخول، يتم التوجيه إلى `teacher.dashboard`.

### ملاحظات
- الأدمن يستطيع أيضاً إنشاء مدرس مباشرة بدون طلب تسجيل (من صفحة إدارة المدرسين).
- في حالة الإنشاء المباشر، الحالة الافتراضية `active` والمدرس يستطيع الدخول فوراً.

## Workflow 2: رفض المدرس

**المصدر:** `admin_features.md` (Section 7.3)

### السيناريو الكامل

1. المدرس يسجل حساباً جديداً ← `status = 'pending'`.
2. الحساب يظهر في صفحة طلبات المدرسين عند الأدمن.
3. الأدمن يضغط على زر "رفض" (`POST /admin/teachers/{user}/reject`).
4. النظام يتحقق: `$user->role === 'teacher'` و `$user->status === 'pending'`.
5. يظهر حقل اختياري لسبب الرفض (`rejection_reason`، max 500 characters).
6. يمكن للأدمن كتابة سبب الرفض أو تركه فارغاً.
7. يتم تغيير الحالة إلى `rejected`.
8. يتم تسجيل العملية في Activity Log (`teacher_rejected` مع السبب إن وجد).
9. المدرس يتلقى إشعاراً (نظامي) بأن طلبه قد تم رفضه.
10. المدرس لا يستطيع تسجيل الدخول (الحالة `rejected` تمنع الدخول).

### قرار المالك
- **لا نحتاج** صفحة History مستقلة لطلبات المدرسين المقبولة أو المرفوضة.
- يكفي إمكانية الفلترة داخل شاشة إدارة المدرسين حسب الحالة (Pending / Active / Rejected / Suspended).

## Workflow 3: إنشاء مجموعة

**المصدر:** `teacher_features.md` (Section 4)

### السيناريو الكامل

1. المدرس يفتح صفحة إنشاء مجموعة جديدة.
2. يملأ البيانات المطلوبة:
   - العنوان (مطلوب، حتى 255 حرف)
   - الوصف (اختياري)
   - اليوم (مطلوب)
   - وقت البدء (مطلوب)
   - وقت النهاية (مطلوب)
   - نوع الجنس (مطلوب: boys/girls/mixed)
   - مستوى الصف (مطلوب)
   - أقصى عدد طلاب (مطلوب، integer، min 1)
3. يتم ربط المجموعة تلقائياً بالترم الأكاديمي النشط للمدرس.
4. يتم إنشاء المجموعة (`StudyGroup`) مع `teacher_id` المطابق للمدرس الحالي.
5. الحالة الافتراضية للمجموعة: `active`.
6. المجموعة تظهر في قائمة مجموعات المدرس.
7. المجموعة تظهر للطلاب عند إدخال كود المدرس في صفحة التسجيل (إذا كانت `active`).
8. المجموعة تظهر في صفحة المجموعات المتاحة للطالب (`GET /student/groups`).

### ملاحظات
- المدرس يمكنه تعديل المجموعة (نفس الحقول + حالة المجموعة).
- **قاعدة:** `max_students` لا يمكن أن يكون أقل من عدد الطلاب الحاليين.
- إذا تغير الموعد (يوم، وقت بداية، وقت نهاية) → إرسال إشعارات للطلاب.
- المدرس يتلقى إشعار تأكيد واحد فقط (غير مزعج).

## Workflow 4: انضمام الطالب

**المصدر:** `student_features.md` (Section 2 + Section 5)

### السيناريو الكامل

1. الطالب يزور صفحة التسجيل (`GET /register/student`).
2. يدخل كود المدرس في Query Parameter `?code=XXXXXX`.
3. النظام يبحث عن مدرس بهذا الكود (يجب أن يكون `active`).
4. إذا كان الكود صحيحاً:
   - تظهر مجموعات ذلك المدرس النشطة (`status = 'active'`).
   - يعرض لكل مجموعة: الاسم، المرحلة، اليوم، الوقت، النوع.
5. إذا كان الكود خاطئاً:
   - تظهر رسالة "كود المدرس غير صحيح".
6. الطالب يختار مجموعة واحدة من القائمة.
7. الطالب يملأ نموذج التسجيل:
   - `teacher_code` (required)
   - `group_id` (required)
   - `name` (required)
   - `mobile` (required)
   - `parent_mobile` (required)
   - `password` (required, confirmed)
8. النظام يتحقق من:
   - صلاحية كود المدرس (نشط).
   - المجموعة تابعة لذلك المدرس ونشطة.
   - المجموعة غير ممتلئة (`max_students`).
   - لا يوجد تسجيل مكرر لنفس رقم الهاتف في نفس المجموعة.
9. يتم إنشاء حساب طالب جديد:
   - `student_code` فريد (STD-000001...).
   - `card_id` فريد (CARD-XXXXXXXX).
   - `qr_token` فريد.
10. يتم إنشاء `GroupEnrollment` مع `status = 'enrolled'`.
11. يتم تسجيل الدخول تلقائياً بعد التسجيل.
12. يتم وضع `active_student_id` في الجلسة.
13. الطالب يرى بيانات مجموعته في لوحة التحكم.

### ملاحظات
- الطالب يمكنه التسجيل عند أكثر من مدرس (حساب مستقل لكل مدرس).
- الطالب يمكنه التبديل بين حساباته المتعددة.

## Workflow 5: إضافة مساعد

**المصدر:** `teacher_features.md` (Section 15) + `assistant_features.md` (Section 1, 2)

### السيناريو الكامل

1. المدرس يفتح صفحة إدارة المساعدين.
2. يضغط على زر "إضافة مساعد جديد".
3. يملأ البيانات المطلوبة:
   - الاسم (required)
   - اسم المستخدم (username، فريد، required)
   - كلمة المرور (required)
   - رقم الهاتف (اختياري)
4. يختار صلاحيات المساعد (checkboxes):
   - `can_take_attendance`: تسجيل الحضور
   - `can_manage_students`: إدارة الطلاب
   - `can_upload_resources`: رفع الموارد
   - `can_manage_reservations`: إدارة الحجوزات
   - `can_restore_students`: استرجاع الطلاب
   - `can_view_groups`: مشاهدة المجموعات
   - `can_manage_lessons`: إدارة الدروس
   - `can_manage_exams`: إدارة الامتحانات
   - `can_manage_grades`: إدارة الدرجات
5. يتم إنشاء حساب المساعد:
   - `teacher_id` = المدرس الحالي
   - `status = 'active'`
   - يتم إنشاء سجل في `assistant_permissions` مع الصلاحيات المختارة.
6. يتم إرسال إشعار للمدرس (تم إنشاء مساعد جديد).
7. يتم إرسال إشعار للمساعد (تم إنشاء حسابك كمساعد).
8. المساعد يستطيع تسجيل الدخول عبر `/assistant/login` باستخدام username + password.
9. المساعد يستخدم Guard منفصل (`assistant`).

### ملاحظات
- المساعد لا يستطيع تسجيل نفسه بنفسه (فقط المدرس ينشئه).
- كل مساعد مرتبط بمدرس واحد فقط.
- المساعد لا يستطيع إنشاء مساعدين آخرين.

## Workflow 6: إدارة صلاحيات المساعد

**المصدر:** `teacher_features.md` (Section 15) + `assistant_features.md` (Section 4)

### السيناريو الكامل

1. المدرس يفتح صفحة تعديل المساعد.
2. يرى قائمة الصلاحيات الحالية (checkboxes).
3. يمكنه:
   - تفعيل صلاحية جديدة (check).
   - إلغاء تفعيل صلاحية حالية (uncheck).
   - تعديل أي صلاحية في أي وقت.
4. عند الحفظ:
   - يتم تحديث سجل `assistant_permissions`.
   - الصلاحيات تصبح فورية: إذا سحب المدرس صلاحية، يفقد المساعد الوصول فوراً.
   - يتم إرسال إشعار للمساعد (تم تحديث صلاحياتك).
5. آلية التحقق من الصلاحية:
   - **على مستوى Route:** Middleware `assistant:<permission>`.
   - **على مستوى Controller:** دوال التحقق (`authorizeSession`, `authorizeEnrollment`, إلخ).
   - **على مستوى Model:** `Assistant::canPerm(string $permission): bool`.
6. إذا حاول المساعد الوصول إلى صفحة لا يملك صلاحيتها → 403 "غير مصرح لك بتنفيذ هذا الإجراء".

### قواعد الصلاحيات

| الصلاحية | تسمح بـ | لا تسمح بـ |
|----------|---------|------------|
| `can_take_attendance` | عرض جلسات الحضور، إنشاء جلسة جديدة، تسجيل حضور الطلاب، إغلاق الجلسة، **إعادة فتح جلسة مغلقة**، تعديل الحضور، إعادة الإغلاق | — |
| `can_manage_students` | عرض الطلاب، نقل الطالب بين المجموعات | إضافة طالب جديد، إزالة طالب، عمليات bulk |
| `can_upload_resources` | إدارة الموارد الكاملة (رفع، عرض، تعديل، حذف، استرجاع، تحميل، بحث، فلترة، تثبيت، نسخ) | — |
| `can_manage_reservations` | إدارة الحجوزات الكاملة (عرض، إنشاء، تعديل، إلغاء، بحث، فلترة، تسليم) | — |
| `can_restore_students` | استرجاع الطلاب المحذوفين | — |
| `can_view_groups` | عرض المجموعات مع عدد المسجلين | إنشاء، تعديل، حذف، أرشفة المجموعات |
| `can_manage_lessons` | إدارة الدروس الكاملة (CRUD، ترتيب Move Up/Down، Drag & Drop، Soft Delete، Restore، Recycle Bin) | — |
| `can_manage_exams` | إدارة الامتحانات الكاملة (إنشاء، تعديل، نشر، إغلاق، أرشفة، استرجاع، حذف، بنك أسئلة) | — |
| `can_manage_grades` | إدارة درجات الطلاب (عرض، تعديل) مع إشعار المدرس عند التعديل | — |

### قرار المالك
- **اعتماد صلاحية `can_manage_grades` رسمياً** وتضاف إلى قاعدة البيانات ونظام الصلاحيات.
- الأدمن لا يستطيع تعديل صلاحيات المساعد — صلاحياته يحددها المدرس فقط.
- كل صلاحية مستقلة: امتلاك `can_manage_students` لا يمنح `can_restore_students` تلقائياً.

## Workflow 7: الحضور

**المصدر:** `teacher_features.md` (Section 6) + `assistant_features.md` (Section 6)

### السيناريو الكامل

1. **إنشاء جلسة حضور:**
   - المدرس (أو المساعد بصلاحية `can_take_attendance`) يفتح صفحة إنشاء جلسة حضور.
   - يختار المجموعة (يجب أن تكون تابعة للمدرس).
   - يحدد رقم الدرس (`lesson_number`).
   - **قاعدة:** لا يمكن أن تكون هناك أكثر من جلسة مفتوحة لنفس المجموعة. إذا كانت موجودة، يتم إعادة توجيه لها.
   - يتم إنشاء الجلسة بـ `status = 'open'`، `attendance_date = today`، `started_at = now`.

2. **تسجيل الحضور:**
   - المسح عبر QR code للطالب.
   - أو إدخال `student_id` أو `student_code` يدوياً.
   - إذا تم تقديم `qr_token`، يجب أن يطابق `qr_token` الخاص بالتسجيل (enrollment).
   - يُسجل كـ `present` إذا تم أثناء الجلسة المفتوحة.
   - **حالات الرفض:**
     - الطالب غير مسجل في المجموعة → رفض مع رسالة خطأ.
     - كود QR خاطئ → رفض.
     - محاولة تسجيل مزدوج → رفض (تم تسجيله مسبقاً).
     - الجلسة مغلقة → لا يمكن تسجيل حضور (يجب التعديل اليدوي).

3. **إغلاق الجلسة:**
   - المدرس (أو المساعد) يضغط على زر "إغلاق الجلسة".
   - يتم تغيير الحالة إلى `closed`.
   - كل الطلاب المسجلين في المجموعة بدون سجل حضور يصبحون `absent` تلقائياً.
   - تطبيق قاعدة الغياب المتتالي: غيابان متتاليان → إزالة تلقائية من المجموعة (`inactive_due_to_absence`).

4. **التصحيح اليدوي:**
   - متاح فقط للجلسات المغلقة.
   - يمكن تغيير الحالة بين `present` و `absent`.
   - عند التغيير إلى `absent`: تطبيق قاعدة الغياب مرة أخرى.
   - عند التغيير إلى `present`: إزالة حالة الإزالة (إذا كانت ناتجة عن الغياب).

5. **إعادة فتح Session:**
   - حتى بعد إغلاق Session الحضور:
     - يستطيع المدرس إعادة فتحها.
     - يستطيع تعديل الحضور.
     - يستطيع إعادة الإغلاق مرة أخرى.
   - **المساعد الذي يملك صلاحية `can_take_attendance` يسمح له أيضاً بإعادة فتح جلسة الحضور المغلقة وتعديل الحضور ثم إعادة إغلاقها.**

### قرار المالك
- المساعد الذي يملك صلاحية `can_take_attendance` يسمح له أيضاً بإعادة فتح جلسة الحضور المغلقة وتعديل الحضور ثم إعادة إغلاقها.

## Workflow 8: الدروس

**المصدر:** `teacher_features.md` (Section 7)

### السيناريو الكامل

1. **إنشاء درس:**
   - المدرس (أو المساعد بصلاحية `can_manage_lessons`) يفتح صفحة إنشاء درس.
   - يملأ البيانات:
     - عنوان الدرس (مطلوب)
     - وصف (اختياري)
     - مجموعة (مطلوبة، يجب أن تكون للمدرس)
     - ترتيب العرض (اختياري، يُحسب تلقائياً كـ max+1)
     - حالة تفعيل (`is_active`)
   - يتم إنشاء الدرس مع `teacher_id` المطابق.

2. **عرض الدروس:**
   - تظهر الدروس مرتبة حسب `display_order`.
   - كل درس يعرض مع مصادره (Resources).
   - فقط الدروس `is_active = true` تظهر للطلاب.

3. **تعديل درس:**
   - نفس الحقول عند الإنشاء.
   - المدرس يمكنه تعديل دروسه فقط.

4. **ترتيب الدروس:**
   - **Move Up / Move Down:** رسمي ومعتمد.
   - **Drag & Drop:** رسمي ومعتمد.
   - كلا الطريقتين رسميتان.
   - يعتمد على `display_order` (عدد صحيح).

5. **حذف درس:**
   - حذف ناعم (soft delete).
   - عند الحذف: تحديث resources المرتبطة لجعل `lesson_id = null`.
   - لا يتم حذف المصادر المرتبطة بالدرس.
   - الدرس ينتقل إلى سلة المحذوفات (Recycle Bin).

6. **استرجاع درس:**
   - من سلة المحذوفات.
   - استرجاع الدرس مع إمكانية إعادة ربط المصادر.

7. **حذف نهائي:**
   - من سلة المحذوفات.
   - حذف نهائي لا يمكن التراجع عنه.

### قرار المالك
- **المساعد الذي يملك `can_manage_lessons` يمتلك كامل إدارة الدروس** بما فيها:
  - Move Up / Move Down
  - Drag & Drop
  - Soft Delete
  - Restore
  - Recycle Bin

## Workflow 9: الموارد

**المصدر:** `teacher_features.md` (Section 8) + `student_features.md` (Section 8)

### السيناريو الكامل

1. **رفع مورد:**
   - المدرس (أو المساعد بصلاحية `can_upload_resources`) يفتح صفحة إنشاء مورد.
   - يختار نوع المورد:
     - `pdf` / `image` / `zip` / `other` → رفع ملف (max 20MB).
     - `google_drive` / `external_link` / `video_link` → إدخال URL.
   - يملأ البيانات:
     - العنوان (مطلوب)
     - الوصف (اختياري)
     - الملف أو الرابط (حسب النوع)
     - تاريخ النشر (اختياري)
     - تاريخ انتهاء الصلاحية (اختياري)
     - المجموعات المستهدفة (Target Scopes)
   - يختار نطاق الاستهداف:
     - `group`: مجموعات محددة.
     - `stage`: مستوى دراسي محدد.
     - `gender`: نوع الجنس.
     - `all`: كل الطلاب.
   - يتم إنشاء المورد مع `teacher_id`، `academic_term_id` (الترم النشط)، `pinned = false`، `status = 'visible'`.
   - يتم إنشاء `ResourceTarget` records لكل مجموعة محددة.

2. **ظهور المورد للطالب:**
   - الطالب يرى المورد في صفحة المصادر (`student.resources.home`).
   - شروط الظهور:
     - المورد مرتبط بمدرس المجموعة النشطة للطالب.
     - `status = 'visible'`.
     - غير منتهي الصلاحية (`expires_at`).
     - يستهدف الطالب عبر أحد النطاقات (targets).
   - للطلاب غير النشطين: تظهر فقط الموارد المنشورة قبل تاريخ الإلغاء.

3. **تحميل المورد:**
   - الطالب يضغط على رابط التحميل.
   - يتم التحميل عبر `asset('storage/' . $resource->file_path)`.
   - لا توجد صلاحيات إضافية للتحميل.

4. **تعديل مورد:**
   - المدرس يمكنه تعديل بيانات المورد.
   - تغيير الحالة: `visible` / `hidden` / `archived`.
   - تحديث `publish_date` أو `expires_at`.

5. **تثبيت مورد (Pin):**
   - `pinned: true/false`.
   - حد أقصى 5 مصادر مثبتة للمدرس.
   - عند التثبيت، إذا تجاوز 5، الأحدث يلغي التثبيت الأقدم.

6. **نسخ مورد:**
   - نسخ المورد مع كل أهدافه (targets).
   - العنوان يُضاف إليه " (نسخة)".

7. **حذف مورد:**
   - Soft Delete.
   - يمكن استرجاعه.

8. **استرجاع مورد:**
   - من سلة المحذوفات.

### قرار المالك
- **المساعد الذي يملك `can_upload_resources` يمتلك الإدارة الكاملة للموارد:**
  - Create
  - List
  - Edit
  - Delete
  - Restore
  - Download
  - Search
  - Filter
  - Pin
  - Copy

## Workflow 10: الحجوزات

**المصدر:** `teacher_features.md` (Section 10) + `student_features.md` (Section 12)

### السيناريو الكامل

1. **إنشاء حجز:**
   - المدرس (أو المساعد بصلاحية `can_manage_reservations`) يفتح صفحة إنشاء حجز.
   - يختار نوع الحجز: `printed_notes` / `books` / `booklets` / `practice_sheets` / `external_material` / `other`.
   - يملأ البيانات:
     - العنوان (مطلوب)
     - الوصف (اختياري)
     - الكمية (0 = غير محدود)
     - تاريخ الفتح (اختياري)
     - تاريخ الإغلاق (اختياري)
     - المجموعات المستهدفة (مطلوبة)
   - الحالة الافتراضية: `draft`.

2. **فتح الحجز:**
   - المدرس يغير الحالة إلى `open`.
   - الطلاب يمكنهم رؤية الحجز والحجز عليه.

3. **ظهور الحجز للطالب:**
   - الطالب يرى الحجوزات المفتوحة لمجموعته النشطة (`student.reservations.index`).
   - لكل حجز: العنوان، الوصف، المدرس، تاريخ الإغلاق، الكمية المتبقية، الحالة.

4. **حجز الطالب:**
   - الطالب يضغط على زر الحجز في صفحة تفاصيل الحجز.
   - يتم إنشاء `ReservationItem` مع `student_id`، `group_id`، `delivery_status = 'pending'`.
   - إذا كان الحجز محدود الكمية، يتم إغلاق الحجز تلقائياً إذا وصلت الكمية للصفر.

5. **إلغاء الحجز (من قبل الطالب):**
   - الطالب يستطيع إلغاء الحجز.
   - عند الإلغاء:
     - زيادة الكمية المتاحة إذا كان الحجز محدوداً.
     - إرسال Notification للمدرس.

6. **إغلاق الحجز:**
   - المدرس يغير الحالة إلى `closed`.
   - الطلاب لا يمكنهم الحجز أكثر.

7. **تسليم الحجز:**
   - المدرس يحدد حالة التسليم يدوياً (`pending` / `delivered`).
   - يمكن الإلغاء (undo delivery).

8. **أرشفة الحجز:**
   - الحجز المؤرشف: read-only history.
   - لا يمكن تعديل حجز مؤرشف.
   - لا يمكن حذف حجز مؤرشف (يجب force-delete).

9. **إعادة فتح الحجز:**
   - من `closed` إلى `open`.

### قرار المالك
- **الطالب يستطيع إلغاء الحجز.** عند الإلغاء: زيادة الكمية المتاحة إذا كان الحجز محدوداً + إرسال Notification للمدرس.
- **المساعد الذي يملك `can_manage_reservations` يمتلك الإدارة الكاملة للحجوزات:**
  - Create / List / Edit / Cancel / Search / Filter / Delivery

## Workflow 11: الامتحانات

**المصدر:** `teacher_features.md` (Section 9) + `student_features.md` (Section 9)

### السيناريو الكامل

1. **إنشاء امتحان:**
   - المدرس (أو المساعد بصلاحية `can_manage_exams`) يفتح صفحة إنشاء امتحان.
   - يملأ البيانات:
     - العنوان (مطلوب)
     - الوصف (اختياري)
     - المدة بالدقائق (مطلوب)
     - وقت البدء (اختياري)
     - وقت النهاية (اختياري، بعد وقت البدء)
     - المجموعات المستهدفة (مطلوبة، array)
   - الحالة الافتراضية: `draft`.

2. **إدارة الأسئلة:**
   - إضافة أسئلة يدوياً (4 خيارات + إجابة صحيحة + درجة).
   - أو اختيار من بنك الأسئلة (خاص بالمدرس).
   - ترتيب الأسئلة (`sort_order`).
   - حذف أسئلة فردية.

3. **نشر الامتحان:**
   - تغيير الحالة إلى `visible`.
   - إرسال إشعار للطلاب المستهدفين.
   - يمكن للطلاب بدء المحاولة بعد النشر.

4. **ظهور الامتحان للطالب:**
   - الطالب يرى الامتحان في صفحة الامتحانات (`student.exams.index`).
   - حالات الامتحان:
     - "سيبدأ لاحقاً" إذا كان `starts_at > now()`.
     - "منتهي" إذا كان `ends_at < now()`.
     - "تم الحل" إذا كان للطالب محاولة بحالة finished.
     - "متاح للبدء" إذا كان الوقت الحالي ضمن النطاق ولم يتم حله.

5. **بدء المحاولة:**
   - الطالب يضغط على "ابدأ الامتحان".
   - التحقق من أن الامتحان يستهدف مجموعة الطالب.
   - التحقق من أن الامتحان مفتوح (`isOpen`).
   - إنشاء محاولة جديدة (`ExamAttempt`) إذا لم توجد.
   - إذا كانت هناك محاولة سابقة منتهية → إعادة توجيه إلى النتيجة مع رسالة "لقد أديت هذا الامتحان مسبقاً".
   - إذا كانت المحاولة موجودة ولم تنته → يستأنف الامتحان.

6. **أداء الامتحان:**
   - صفحة واحدة مع كل الأسئلة.
   - تنقل بين الأسئلة (سابق / تالي).
   - Auto-save عند تغيير الإجابة (AJAX).
   - Timer (عد تنازلي من `started_at + duration_minutes`).
   - عند انتهاء الوقت: يتم تقديم الامتحان تلقائياً.
   - حماية Anti-cheat: منع copy, cut, context menu, select.
   - تحذير عند إغلاق المتصفح (beforeunload).

7. **الخروج من الامتحان:**
   - إذا خرج الطالب من الامتحان لأي سبب:
     - لا يستطيع الدخول مرة أخرى نهائياً.
     - تعتبر المحاولة منتهية.
     - يعتمد التصحيح على ما تم حفظه.
   - يمكن للطالب الضغط على "خروج" → يتم وضع `status = 'cancelled'`.

8. **تقديم الامتحان:**
   - جمع كل الإجابات من الـ form.
   - لكل سؤال: مقارنة الإجابة المختارة مع `correct_answer`.
   - حساب الدرجة (score) والمجموع الكلي (total_marks).
   - حفظ الإجابات في `ExamAnswer` (updateOrCreate).
   - تحديث المحاولة: `finished_at`, `score`, `total_marks`, `status = 'finished'`.
   - إشعار المدرس (مرة واحدة فقط عند أول finish من أي طالب).

9. **عرض النتيجة:**
   - إذا كان `show_result_immediately = true`: عرض الدرجة (score/total) مع وقت التسليم.
   - إذا كان `show_result_immediately = false`: عرض صفحة "result-hidden" (لا تظهر الدرجة).
   - **لا يتم عرض إجابات الطالب الصحيحة/الخاطئة.**

10. **مراجعة المحاولات السابقة:**
    - إضافة صفحة لمراجعة محاولات الطالب السابقة.
    - تعرض جميع الامتحانات التي قام بها الطالب مع النتائج.

11. **تعديل الدرجة:**
    - المدرس يستطيع تعديل الدرجات حتى بعد نشرها.
    - نشر الدرجات لا يعني أنها أصبحت نهائية.
    - أي تعديل بعد النشر يجب أن يحدث بشكل طبيعي.

12. **إشعارات الامتحان:**
    - عند نشر الامتحان: إشعار للطلاب المستهدفين.
    - عند أول تسليم: إشعار للمدرس.
    - عند تعديل الدرجة بواسطة المساعد: إشعار للمدرس.

13. **إغلاق الامتحان:**
    - تغيير الحالة إلى `hidden`.
    - الطلاب لا يمكنهم بدء محاولات جديدة.
    - المحاولات الجارية تستمر.

14. **حذف الامتحان:**
    - Soft Delete.
    - ينتقل الامتحان إلى الأرشيف لمدة 7 أيام.
    - يستطيع المدرس استرجاعه خلال 7 أيام.
    - بعد انتهاء المدة يمكن حذفه نهائياً.

### قرار المالك
- **المساعد الذي يملك `can_manage_exams` يمتلك الإدارة الكاملة للامتحانات** بما فيها إنشاء الامتحان.
- **إضافة صفحة مراجعة محاولات الطالب السابقة.**

## Workflow 12: الدرجات

**المصدر:** `teacher_features.md` (Section 11)

### السيناريو الكامل

1. **تصحيح الامتحان:**
   - بعد تقديم الطالب للامتحان، يتم حساب الدرجة تلقائياً.

2. **نشر الدرجات:**
   - المدرس ينشر الدرجات (تظهر للطالب).
   - نشر الدرجات لا يعني أنها أصبحت نهائية.

3. **تعديل الدرجة بعد النشر:**
   - المدرس يستطيع تعديل الدرجات حتى بعد نشرها.
   - أي تعديل بعد النشر يجب أن يحدث بشكل طبيعي.

4. **تعديل الدرجة بواسطة المساعد:**
   - المساعد الذي يملك صلاحية `can_manage_grades` يستطيع تعديل الدرجات.

   - يظهر فقط الامتحانات التي حالتها `finished`.

6. **قيود الدرجات:**
   - المدرس يمكنه الوصول فقط لدرجات طلاب مجموعاته.
   - الطالب يرى فقط درجاته الخاصة.
   - الطالب لا يستطيع تعديل أي درجة.

### قرار المالك
- **اعتماد صلاحية `can_manage_grades` رسمياً** وتضاف إلى قاعدة البيانات ونظام الصلاحيات.

## Workflow 13: حذف الطالب من المجموعة

**المصدر:** `teacher_features.md` (Section 5.3)

### السيناريو الكامل

1. **إزالة الطالب:**
   - المدرس يختار طالباً من قائمة طلاب المجموعة.
   - يضغط على زر "إزالة".
   - يتم تغيير حالة الـ enrollment إلى `inactive_due_to_teacher`.
   - يتم إرسال إشعار للطالب بأنه تمت إزالته.

2. **الأرشفة:**
   - عند الحذف، يتم أرشفة:
     - الحضور
     - الدرجات
     - الامتحانات
     - الموارد المرتبطة
   - لا يتم حذف البيانات نهائياً.

3. **استرجاع الطالب:**
   - المدرس يمكنه استرجاع الطالب لاحقاً.
   - إذا عاد الطالب لنفس المجموعة:
     - تعود جميع بياناته كما كانت (الحضور، الدرجات، الامتحانات، الموارد).

4. **حالات الطالب بعد الإزالة:**
   - `inactive_due_to_teacher`: أزالهم المدرس يدوياً.
   - `inactive_due_to_absence`: أزالهم النظام بسبب الغياب المتتالي.
   - `removed`: تمت إزالتهم بطريقة أخرى.

### ملاحظات
- المساعد بصلاحية `can_manage_students` لا يستطيع إزالة الطلاب (فقط نقلهم).
- المساعد بصلاحية `can_restore_students` يستطيع استرجاع الطلاب.

## Workflow 14: نقل الطالب

**المصدر:** `teacher_features.md` (Section 5.6, 5.7) + `student_features.md` (Section 6)

### السيناريو الكامل

1. **نقل يدوي (من المدرس):**
   - المدرس يختار طالباً من قائمة الطلاب.
   - يختار مجموعة وجهة (يجب أن تكون تابعة للمدرس نفسه، `active`، وغير ممتلئة).
   - يتم نقل الطالب:
     - التسجيل القديم يُلغى.
     - تسجيل جديد يُنشأ في المجموعة الهدف.
     - يتم تسجيل العملية في `EnrollmentHistory`.
   - **ما ينتقل مع الطالب:**
     - الحضور
     - الدرجات
     - الامتحانات
     - الحجوزات
     - أي بيانات أكاديمية مرتبطة
   - الطالب لا يبدأ من الصفر، بل ينتقل معه كامل سجله.

2. **نقل يدوي (من المساعد):**
   - المساعد بصلاحية `can_manage_students` يستطيع نقل الطالب.
   - نفس الشروط: المجموعة الهدف تابعة لنفس المدرس، `active`، غير ممتلئة.

3. **نقل عبر طلب الطالب (Transfer Request):**
   - الطالب يضغط على "طلب نقل إلى مجموعة أخرى" من لوحة التحكم.
   - تظهر له قائمة المجموعات النشطة الأخرى لنفس المدرس.
   - يختار مجموعة جديدة ويرسل الطلب.
   - حالة الـ enrollment تتغير إلى `pending_transfer` مع `requested_group_id`.
   - المدرس يستعرض الطلبات المعلقة.
   - **قبول الطلب:** يتم النقل فوراً.
   - **رفض الطلب:** يعود الطالب لمجموعته الأصلية (حالة `enrolled`).

4. **Bulk Move:**
   - المدرس يستطيع نقل عدة طلاب مرة واحدة.

### قيود النقل
- لا يمكن نقل الطالب إلى مجموعة تابعة لمدرس آخر.
- لا يمكن النقل إلى مجموعة ممتلئة.
- لا يمكن إرسال طلب نقل إذا لم يكن الطالب في حالة `enrolled`.

## Workflow 15: حذف المجموعة

**المصدر:** `teacher_features.md` (Section 4.6)

### السيناريو الكامل

1. **التحذير:**
   - المدرس يضغط على زر "حذف" للمجموعة.
   - يظهر تحذير واضح قبل الحذف (تأكيد).

2. **Soft Delete:**
   - يتم تغيير حالة المجموعة إلى `archived`.
   - لا يتم حذف بيانات الطلاب.
   - تبقى جميع البيانات محفوظة (الحضور، الدرجات، الامتحانات، الموارد).
   - المجموعة تنتقل إلى الأرشيف.

3. **بعد الحذف:**
   - المجموعة لا تظهر في القوائم النشطة.
   - لا يمكن للمجموعة المؤرشفة أن تكون نشطة مرة أخرى إلا عبر restore.

4. **الاسترجاع:**
   - المدرس يمكنه استرجاع المجموعة.
   - إعادة المجموعة إلى حالة `active`.
   - متاحة فقط للمجموعات المؤرشفة.

### قرار المالك
- **الأرشفة غير مرتبطة بمدة زمنية.**
- تبقى المجموعة مؤرشفة حتى يحذفها المدرس نهائياً أو يسترجعها.

### قيود الحذف
- المدرس يمكنه حذف مجموعاته فقط.

---

## Workflow 16: النسخ الاحتياطية

**المصدر:** `admin_features.md` (Section 11)

### السيناريو الكامل

1. **إنشاء نسخة احتياطية:**
   - الأدمن يفتح صفحة النسخ الاحتياطية (`GET /admin/backup`).
   - يضغط على زر "إنشاء نسخة احتياطية".
   - النظام يتحقق من توفر `mysqldump` (عبر `where`/`which`).
   - يتم تنفيذ `mysqldump` عبر `exec()`.
   - يتم حفظ الملف في `storage/app/backups/`.
   - يتم إنشاء سجل في `Backup` model (filename, path, size, type).
   - يتم تسجيل العملية في Activity Log (`backup_created`).

2. **عرض النسخ الاحتياطية:**
   - جدول مع اسم الملف، الحجم، النوع، تاريخ الإنشاء.
   - مع Pagination.

3. **تحميل نسخة احتياطية:**
   - الأدمن يضغط على زر "تحميل".
   - يتم التحميل عبر `response()->download()`.

4. **حذف نسخة احتياطية:**
   - الأدمن يضغط على زر "حذف".
   - يتم حذف الملف والسجل من قاعدة البيانات.
   - يتم تسجيل العملية في Activity Log (`backup_deleted`).

5. **استرجاع نسخة احتياطية (Restore):**
   - معتمد رسمياً كجزء من الإصدار الأساسي.
   - يتطلب شاشة تأكيد قوية قبل التنفيذ.

6. **جدولة النسخ الاحتياطية:**
   - معتمدة رسمياً كجزء من الإصدار الأساسي.
   - يومي / أسبوعي / شهري.

### قرار المالك
- **اعتماد Restore وجدولة النسخ الاحتياطية (يومي / أسبوعي / شهري) كجزء من الإصدار الأساسي** وليس Sprint لاحق.

## Workflow 18: تسجيل النشاط (Activity Log)

**المصدر:** `admin_features.md` (Section 8)

### ما الذي يسجل

| الإجراء (action) | التصنيف (category) | الوصف | من يسجله |
|------------------|---------------------|-------|----------|
| `teacher_approved` | Teacher | تم الموافقة على المدرس: {name} | الأدمن |
| `teacher_rejected` | Teacher | تم رفض المدرس: {name} - السبب: {reason} | الأدمن |
| `teacher_activated` | Teacher | تم تفعيل المدرس: {name} | الأدمن |
| `teacher_deactivated` | Teacher | تم إلغاء تفعيل المدرس: {name} | الأدمن |
| `teacher_suspended` | Teacher | تم تعليق المدرس: {name} | الأدمن |
| `teacher_restored` | Teacher | تم استعادة المدرس: {name} | الأدمن |
| `teacher_deleted` | Teacher | تم حذف المدرس: {name} | الأدمن |
| `settings_updated` | Administration | تم تحديث إعدادات المنصة | الأدمن |
| `backup_created` | Administration | تم إنشاء نسخة احتياطية: {filename} | الأدمن |
| `backup_deleted` | Administration | تم حذف النسخة الاحتياطية: {filename} | الأدمن |
| جميع عمليات المساعدين | — | تسجل تلقائياً | المساعد |
| جميع عمليات Impersonation | — | تسجل بالكامل | الأدمن |

### متى يسجل
- كل عملية من عمليات الأدمن على المدرسين تسجل تلقائياً.
- كل عملية تحديث إعدادات المنصة تسجل.
- كل عملية إنشاء أو حذف نسخة احتياطية تسجل.
- كل عملية Impersonation تسجل بالكامل.
- جميع عمليات المساعدين تسجل (مع `actor_type = 'assistant'`).

### هيكل البيانات
- Model `ActivityLog` يحتوي على: `actor_id`, `actor_type`, `actor_type_label`, `action`, `category`, `description`, `ip_address`, `owner_id`, `owner_type`.
- دالة `::log()` تستخدم `request()->ip()` للحصول على IP.
- يدعم `scopeCategory` و `scopeAction`.

### الإمكانيات المعتمدة (كجزء من النسخة الأساسية)
| الإمكانية | الحالة |
|-----------|--------|
| عرض جميع الأنشطة مع Pagination (30 لكل صفحة) | ✅ موجود |
| فلاتر: category, action, actor_type, date_from, date_to, search | ✅ موجود |
| **حذف السجل** | ✅ معتمد رسمياً |
| **تصدير PDF** | ✅ معتمد رسمياً |
| **تصدير Excel** | ✅ معتمد رسمياً |
| **الفلاتر المتقدمة** | ✅ معتمدة رسمياً |

### قرار المالك
- **اعتماد حذف السجل، تصدير PDF، تصدير Excel، والفلاتر المتقدمة كجزء من النسخة الأساسية.**

## Workflow 19: Login As Teacher (Impersonation)

**المصدر:** `admin_features.md` (Section 17)

### السيناريو الكامل

1. الأدمن يفتح صفحة إدارة المدرسين.
2. يختار مدرساً ويضغط على زر "الدخول كمدرس".
3. يتم تسجيل دخول الأدمن بحساب المدرس بدون كلمة مرور.
4. يظهر Banner واضح في أعلى الصفحة: "أنت تعمل كمدرس".
5. يوجد زر "العودة لحساب الأدمن" في الـ Banner.
6. الأدمن يستطيع الوصول إلى جميع صفحات وموديولات المدرس:
   - المجموعات
   - الطلاب
   - الحضور
   - الدروس
   - الموارد
   - الامتحانات
   - الحجوزات
   - المساعدون
7. عند الضغط على "العودة لحساب الأدمن":
   - يتم تسجيل الخروج من حساب المدرس.
   - العودة إلى لوحة تحكم الأدمن.
8. العملية تسجل بالكامل في Activity Log.

### قواعد Impersonation
- الأدمن يدخل بحساب المدرس بدون كلمة مرور.
- يظهر Banner واضح أن الأدمن يعمل كمدرس.
- يوجد زر "العودة لحساب الأدمن".
- العملية تسجل بالكامل في Activity Log.

## Workflow 20: تغيير كلمة المرور

**المصدر:** `admin_features.md` (Section 18) + `teacher_features.md` (Section 2.3) + `student_features.md` (Section 2) + `assistant_features.md` (Section 2)

### لكل Role

| الـ Role | الحالة | الآلية |
|----------|--------|--------|
| **الأدمن** | ✅ معتمد رسمياً | صفحة مستقلة داخل لوحة الأدمن: Current Password → New Password → Confirm Password |
| **المدرس** | ✅ معتمد رسمياً | صفحة مستقلة: Current Password → New Password → Confirm Password |
| **الطالب** | ✅ معتمد رسمياً | صفحة مستقلة عبر `/password`: Current Password → New Password → Confirm Password |
| **المساعد** | ✅ معتمد رسمياً | صفحة مستقلة: Current Password → New Password → Confirm Password |

### السيناريو العام (جميع الأدوار)
1. المستخدم يفتح صفحة تغيير كلمة المرور.
2. إدخال كلمة المرور الحالية (للتحقق).
3. إدخال كلمة المرور الجديدة.
4. تأكيد كلمة المرور الجديدة.
5. التحقق الكامل من الصحة قبل الحفظ.
6. يتم تحديث كلمة المرور.

### قرار المالك
- **جميع الأدوار تمتلك صفحة مستقلة لتغيير كلمة المرور:** Admin, Teacher, Assistant, Student.
- جميعها تعتمد على: (Current Password → New Password → Confirm Password).
- **إضافة زر "تغيير كلمة المرور" داخل لوحة الأدمن** (Dashboard/Settings) ليكون الوصول إليه مباشراً.
